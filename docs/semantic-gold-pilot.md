## 파일 구성과 스키마

진입점은 [manifest.json](../evaluation/semantic_pilot/manifest.json)이다. manifest와 answers는 평가자 전용이다. 모델에는 지정한 **inputs/SP-NNN.json 하나만** 제공한다. 저장소 전체, manifest, 답안, 이 문서는 모델 입력으로 전달하지 않는다.

| 파일 | 역할 |
| --- | --- |
| [input.schema.json](../evaluation/semantic_pilot/input.schema.json) | JSON Schema Draft 2020-12. 고유 ID, 과제, 출처 구분, 전후 문서 배열, Writing Contract, 보존 의무·노출 범위, 미제공 문맥 |
| [answer.schema.json](../evaluation/semantic_pilot/answer.schema.json) | 기대 판정·오류 유형·중요도·양쪽 근거·이유·허용 대안·검토자별 판정·불일치·재정 기록·검수 상태 |
| [SP-003 입력](../evaluation/semantic_pilot/inputs/SP-003.json)·[잠정 답안](../evaluation/semantic_pilot/answers/SP-003.json) | 전체 원본·목적지의 정상 MOVE 예시. 실제 공개 이동 실행이 아닌 통제된 합성 |
| [공개 전체 스냅샷](../evaluation/semantic_pilot/sources/chatgpt2codex-README.md) | `nanocode00/chatgpt2codex` README, commit `dcc9ed7e18802800ae8b0536a232875b2a29eb05`, Git blob `5c9aeff92d6bbc092d98f84cbe3a0fe29838b6f0`. 파일 전체 SHA-256은 manifest에 고정 |
| [validate.py](../evaluation/semantic_pilot/validate.py)·[자동 테스트](../evaluation/semantic_pilot/test_validate.py) | 데이터 구조·참조·해시·근거 오프셋·검수 승격 조건 검사. 의미 판정 정확도는 검사하지 않음 |

`content`는 실제 UTF-8 텍스트를 JSON에 담으며 문서 해시는 디코딩한 텍스트를 정규화 없이 UTF-8로 인코딩한 SHA-256이다. 공개 원문 파일의 실제 바이트 SHA-256과 Git blob도 별도 확인한다. 답안은 **입력 JSON 파일의 실제 바이트 해시**에 묶는다. 근거 위치 `start/end`는 **0부터 시작하는 Unicode 코드포인트, 반열린 구간, 정규화 없음**이다. 줄 번호는 파생 표시에만 사용하며 `quote == content[start:end]`가 필수다. 정보 누락은 원문의 해당 구간과 수정본의 대응 문맥/전체 짧은 문서를 함께 인용하고 부재 이유를 설명한다.

모든 문서는 `complete / partial / not_provided`를 명시한다. `not_provided`의 본문·해시는 null이며 빈 문서로 취급하지 않는다. `partial`은 실제 빈 결과가 아니라 일부만 제공된 관측이다. 공개 원문 기반이라도 후보와 과제 계약은 AI가 통제해 작성했으며 실제 upstream 변경이 아니다. 공개 출처 해시는 출처 고정을 뜻하고 동작·성능 주장 진실성을 입증하지 않는다.

Writing Contract는 이 평가용 독립 형식이다. Core 계약 필드로 자동 변환하거나 승인 게이트에 연결하지 않는다. `required_information`은 모델에 공개하는 사용자 보존 요구이며, 사례의 기대 오류·판정·해설은 답안에만 있다. `same_document / linked_document / pending_contract`는 현지 노출·링크 허용·계약 미확정을 구분한다. 원문의 나머지 정보도 임의 삭제할 수 없다.

## 이번 사용자 공동 검토 기록

2026-11-10에 사용자가 사례 설명과 전후 문장을 보고 12건 모두 의견을 제공했다. 이는 실제 사람 검토이며, AI 설명·잠정 판단을 함께 본 **공동 검토**다. `answers/*.json`의 `reviews`에 `repository-user`, `blinded_to_ai_proposal: false`로 기록했다. 시점은 대화 날짜만 기록하고 정확한 시간을 추정하지 않았다. 판정·이유는 사용자 의견을 Codex가 요약했고 근거 구간은 기존 문서에서 연결했다. 사용자가 독립적으로 근거 범위를 직접 작성한 기록이나 비노출 검토로 보고하지 않는다.

## 주석·사람 검수 프로토콜

1. 관리자가 입력·스냅샷·계약·해시를 고정하고 각 검토자에게 입력만 배포한다. AI 잠정 답안과 다른 검토자의 판단을 보지 않은 **서로 다른 사람 2명**이 독립 검토한다. 모델/검증기를 돌린 결과를 검토자 판정으로 기록하지 않는다.
2. 양쪽 전체 문서를 읽고 보존 의무를 원문과 후보 위치에 대응한다. 주장 주체·시간·수치·단위·조건·부정·한정·귀속과 남긴 주장의 현지 노출을 확인한다. MOVE는 원본과 목적지 전체 및 기존 목적지 정보까지, 중복 통합은 각 원문의 고유 조건까지 비교한다.
3. `PRESERVED`는 제공 범위와 계약에서 의미가 동등함, `VIOLATION`은 근거로 확인되는 왜곡/필수 정보 손실/근거 없는 추가, `UNRESOLVED`는 의미 판정에 필요한 증거·범위·계약이 부족함을 뜻한다. 확인된 위반이 있다면 다른 미확정 사항 때문에 위반을 가리지 않는다. 보류에는 빠진 자료와 해결 조건을 반드시 적는다.
4. 각 사람은 `reviews`에 ID·시점·입력 해시·판정·이유·근거·AI 답안 비노출 여부를 기록한다. 의견 차이는 `disagreements`에 검토자 ID·쟁점·미해결 사유 또는 해결 근거를 남긴다. 기존 기록과 AI 제안을 덮어쓰지 않는다. 같은 판정이라도 조건/노출 해석이 다르면 불일치를 기록한다.
5. 독립 검토 2건이 모이면 `reviewed`로 기록할 수 있지만 골드 적격으로 승격하지 않는다. 제3의 사람 재정자가 쟁점을 확인하고 `adjudication`에 최종 판정·이유·입력 해시·시점을 기록해야 `adjudicated`가 된다. 해결되지 않는 사례는 보류 라벨로 남기거나 골드 적격에서 제외한다. AI 기대 판정은 비교용 제안으로 그대로 남기고, 사람 기준 판정은 재정 기록을 사용한다.
6. 확장 시에만, 사람 재정과 미해결 의견 차이 없음 및 사례별 포함 승인을 확인한 뒤 `gold_eligible: true`를 허용한다. 재정 결과가 UNRESOLVED여도 근거 부족을 올바르게 식별하는 합의 사례라면 보류 평가 범주로 포함 가능하다. 이번 manifest는 전건 provisional만 허용하므로 **이 PR에서 상태 승격은 하지 않는다.** 입력 수정 시 버전·해시·답안 바인딩을 갱신하고 기존 사람 검수는 무효화해 다시 받는다.

의미 보존과 외부 진실성은 분리한다. 미검증 원문 주장을 정확히 유지했다는 이유로 UNRESOLVED로 만들지 않는다. 예컨대 “추후 검토 예정”을 그대로 유지한 정상 수정은 PRESERVED일 수 있다. 반대로 “현재 지원”으로 바꾸면 외부에서 실제 지원할 가능성과 무관하게 제공 근거 대비 강화다. 정상 표현 변경·문단 순서·정당한 이동은 오류가 아니다. 선택적 문체/배치 선호로 위반을 만들지 않는다.

SP-008은 사용자가 추가 사실이나 삽입 지시를 제공하지 않은 조건에서 평가한다. 사용자 제공 정보·요구가 달라지면 계약과 근거를 함께 다시 검토하며, 지시 준수와 외부 사실 검증을 구분한다. SP-009는 수정 후보를 먼저 구성하고 사후에 링크 연결과 목적지의 정보·조건 보존을 각각 검사할 수 있다. 목적지 미제공에 따른 UNRESOLVED는 최종 의미 보존의 검증 대기이며 후보 생성 금지나 이동 자체의 오류를 뜻하지 않는다. 이 설명은 평가 범위의 구분이며 Core 실행 순서·승인 정책 변경이 아니다.

`REQUIRED_CONDITION_LOSS`와 `UNSUPPORTED_ADDITION`을 따로 기록하고 동일 사례에서 함께 나타나면 둘 다 남긴다. 심각도는 `none`(위반 없음), `minor`(국소적 의미 차이), `major`(과업·조건·주장에 실질 영향), `critical`(핵심 안전/필수 실행 조건에 중대 영향), `undetermined`(증거 부족)로 기록한다. 사례별 영향 근거를 적으며 점수 가중치는 이번에 정하지 않는다. PRESERVED는 Core PASS·전달 승인·실행 성공을 뜻하지 않는다.

## 개발·홀드아웃 확장 계획

| 단계 | 수행·동결 조건 |
| --- | --- |
| 파일럿 사람 검수 | 12건을 두 사람이 독립 검토. 보류 4건에 무엇이 부족한지 합의하고 필요 자료를 확보하되, 별도 버전의 해결된 쌍을 만들어 원래 보류 사례를 보존 |
| 개발용 확장 | 정상·위반·보류, 원문 유형, 조건·귀속·모순·MOVE·통합을 교차 보강. 관련 파생 사례는 동일 source family로 묶고 저장소·원문 단위 중복을 탐지. 정확한 구문 일치를 정답으로 삼지 않음 |
| 독립 홀드아웃 수집 | 이번 파일럿·기존 20/12/14와 원문·저장소 단위 분리. 알려진 5개 저장소와 LogicWrite, 그 fork·mirror·번역·인용 파생 원문을 제외 목록으로 시작. 별도 관리자가 새로운 저장소/출처 계열을 수집하고 개발자/프롬프트 조정에 노출하지 않음 |
| 사전등록·잠금 | 실험 전에 repository/source-family 배정표, 누출 검사, 입력/정답 해시, 검토자·재정 기록, 제외 사유, 표본 수·문서 유형·판정 분포를 고정. 개발용과 홀드아웃은 별도 접근 영역에서 관리. 내용 중복이 발견되면 같은 계열 전체를 한 split으로 이동하거나 제외하고 버전 갱신 |
| 평가 | 사람 재정 판정 대비 3×3 혼동행렬, 정상 오탐·위반 누락·불필요 보류·보류 회수, 오류 유형별 검출, 검토자 일치와 재정 변경 수, 시간·비용을 보고. 분모·표본 수·불확실성과 같은 원문의 상관성을 공개. 모델 출력/기존 검증기 판정으로 정답을 대체하지 않음 |

이번 12건으로 모델 정확도·홀드아웃 품질·Core 2-A 통과를 주장하지 않는다. 공동 검토 이후의 문맥 보완·독립 검수와 독립 자료 확보는 후속 작업이며 파일럿을 넘는 수집·실험은 실행하지 않았다.

## 재현 검사

Python 3.12와 `jsonschema`(로컬 확인 4.10.3)를 사용한다. 필요한 환경에서는 별도 가상환경에 `python3 -m pip install -r evaluation/semantic_pilot/requirements.txt`로 설치한다.

```bash
python3 evaluation/semantic_pilot/validate.py
python3 -m unittest discover -s evaluation/semantic_pilot -p test_validate.py
```

검사는 JSON Schema, 12개 ID와 4/4/4 구성, 파일 누락·고아 참조, 문서/입력/답안/공개 스냅샷 해시, Git blob, 양쪽 근거 범위·인용, 출력 범위, 사람 검토 없는 상태 승격을 확인한다. 자동 검사는 실제 의미 판정·사람 검수·외부 사실 확인·Core 실행·독립 홀드아웃 평가를 수행하지 않는다.
