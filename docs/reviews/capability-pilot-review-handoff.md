## 2. 사용자가 원하는 검수 진행 방식

1. 사용자가 말한 **"한 줄씩"은 검수 목록의 표 한 행 = 사례 한 건(`CP-T1-01` 등)**을 뜻한다. 원문 문장 한 줄마다 승인을 요구하는 뜻이 아니다.
2. 다만 사례의 원문이 길 수 있으므로 **사례 내부에서는 목적·독자 → 원문 주요 구간 → 전체 판단** 순서로 적절히 나누어 확인한다. 문서의 뒤쪽 맥락을 보기 전 불필요한 삭제라고 단정하지 않는다.
3. **입력 우선:** 사용자에게 AI 예상 정답·반례를 먼저 공개하지 않고, 원문과 작성 목적만 제시해 초기 의견을 듣는다. 이후 AI 제안·독립 반례와 대조한다. 답안에 노출된 뒤의 의견을 독립 최초 판단이라고 소급하지 않는다.
4. 사소한 각 문장마다 질문하지 않는다. 한 사례의 중대한 쟁점만 함께 검토하고, 필요한 경우 중간 의견을 메모한다. 사례의 마지막에만 최종 판단/수정 요구를 정리한다.
5. **검수 상태 분리:** 대화 중 의견·보류·검토 제안 ≠ 확정 사용자 판단 ≠ 골드 포함 승인. 사람의 정확한 의사표시 없이 JSON의 `human_*`, `gold_inclusion_approval`을 채우지 않는다.
6. 사례 하나가 마무리될 때마다 이 인수인계 문서에 **사례 ID, 입력 SHA/버전, 주요 쟁점, 사용자 판단의 정확한 범위, 남은 문제, 다음 사례 ID**를 업데이트한다. PR #34의 원본·평가 정답을 대화 메모만으로 변경하거나 병합하지 않는다.

### 추가 논의 — 과제 출력 대상·README 보존 의무 불명확 (2026-11-13)

- **사용자 발언:** “사실 그걸 판단하기에는 컨텍스트가 부족해 보이는게, 저 입력 자체만으로는 README 자체를 재구성하는건지, 아니면 내용 기반으로 새 문서를 작성하는건지 모르겠어. 일단 목적만 봐선 README에 포함될 내용이 맞긴 한데, 제공된 내용이 전부 목적에 부합하는게 아니고 README 안에 들어갈 내용으로는 말이 된단 말야.”
- **판단 핵심:** 과제의 '주요 목적에 바로 필요한 내용'과 'README라는 원래 문서의 기능상 유지할 가치가 있는 내용'은 별개다. Donate/Contributing·예제·링크 등이 표/소개 목표에 직접 기여하지 않더라도 README 전체를 편집하는 경우 남기는 것이 타당할 수 있다. 반면 별도 검토 가이드라면 제외할 수 있다.
- **구조화 입력의 제한적 힌트:** `source_documents[].document_id=draft`는 `editable full README snapshot`, `output_document_ids=[draft]`, `allowed_edit_scope.limits`는 비대상 정보 보존·영향 문서 전체 반환을 명시한다. 형식상 기존 README 수정에 가깝다. 그러나 자연어 요청 '사실·관계 표와 짧은 소개문을 작성'에는 기존 소개와의 결합 방식, 편집 범위/결과물 정체가 충분히 설명되지 않는다.
- **사용자 검토 의견:** 현 과제 정의만으로 원본 README 재구성과 README를 근거로 한 별도 목적별 문서 작성을 확실하게 구별하기 어렵다. 사용자는 어느 쪽을 최종 승인한 것이 아니다.
- **후속 수집/검수 조치 제안(미승인):** 평가 과제에는 `작업 형태(기존 문서 수정/새 문서 작성)`, `결과물 문서 ID·역할`, `원본 보존 의무`, `삽입/수정 대상`, `비대상 정보 처리`를 독자가 읽을 수 있는 지시와 계약 모두에 일치하게 명시한다. 출제 불명확성은 모델이 올바르게 보류해야 하는 의도적 정답 `unresolved`과 구분한다. 이 사례는 사용자와 출제 조건을 확정하기 전 정식 골드로 승인하지 않는다.
- **상태:** CP-T1-01 최초/최종 종합 판단과 골드 포함 승인 여전히 미확정. 기존 PR #34 입력·정답·검수 자료는 수정하지 않음.

### 재정의 논의 — 과제는 처음부터 통합적인 문서 재구성 (2026-11-13)

- **사용자 원문:** “좀더 생각해보니까 과제 유형이라는게 있는게 오히려 이상해보여. 처음부터 과제는 원본 문서와 무관한 내용을 제거하고 다른 문서에 있는 관련 내용은 가져와서 재구성하기였어. 그 과정에서 통일되지 않은 문체나 표현같은것도 같이 정리하는거고.”
- **사용자의 원래 목표 명료화:** LogicWrite는 REMOVE, MOVE, ADD, REVISE 등 액션별로 분리된 지시를 따르는 제품이 아니라, **문서군 전체를 읽고 현재 문서 목적에 맞춰 정보의 포함/제외/재소속/보완/구조/표현을 함께 개선**하는 통합 편집 도구다. 개별 편집 액션은 독립 '과제'가 아니라 필요시 선택하는 수단이다.
- **평가 설계 문제:** 현재 PR #34의 T1~T9는 과제의 주유형에 따라 입력이 구성되고, 상당수는 “제거하라”, “옮겨라”, “보완하라”처럼 발견해야 할 개선 동작을 지시문에 드러낸다. 이는 원래 목표에 대한 능력 평가가 아니라 **정답의 일부를 준 상태에서 지시된 조치를 실행하는 테스트**에 가깝다. T9를 별도 '종합 과제'로 두기보다 **모든 대표 사례를 전체 문서 재구성 과제**로 만드는 것이 사용자의 목표에 더 부합한다.
- **재설계 제안(사용자 검토/승인 전):** 골드의 기본 단위를 `원본문서 + 연관 문서(또는 미제공 시 명시적 공백) + 사용자/독자 맥락 + 편집/조회 권한 + 기대 개선 효과`로 두고, 표준적으로 “이 문서를 독자의 목적에 맞게 개선하고 근거·미해결 사항을 제시하라”고 요청한다. 제거/이동/추가/윤문 액션의 대상이나 정답을 직접 지시하지 않는다. 의미 보존, 원본·목적지 역할, 문서 간 참조, 문체, 안전한 보류를 동시에 평가한다.
- **T1~T9의 향후 역할:** 실제 입력의 '문제 유형' 또는 개별 과제 ID 분류가 아닌 **내부 분석 능력·진단 지표·오류 원인 태그**로 전환하는 안을 제시. 실험 편의상 액션별 작은 합성 단위 테스트는 유지 가능하지만 통합 골드셋의 대표 성능 표본으로 섞지 않는다.
